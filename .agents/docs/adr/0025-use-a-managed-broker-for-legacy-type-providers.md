# Use a managed broker for legacy type providers

Final drop-in type-provider compatibility uses an optional, independently authored managed broker beside the NativeAOT FSharp2 compiler. The native compiler never loads provider assemblies and continues to own parsing, checking, lowering, emission, incremental dependencies, diagnostics, and artifacts. The broker alone executes the public legacy FSharp.Core provider contract and translates provider reflection and quotation objects through a private, bounded, versioned protocol. The broker implementation may reference the matching public FSharp.Core but not FSharp.Compiler.Service, FSharp.Build, official `fsc`, or official compiler implementation; a provider-owned FCS dependency is permitted only as opaque, hashed user input with no broker call path or fallback. Experimental envelopes reject providers explicitly until their declared broker compatibility gate passes. A new snapshot/dependency contract is additive and cannot replace arbitrary legacy-provider compatibility.

Provider instances and opaque handles are never persisted. The provider-visible `IsHostedExecution` and `IsInvalidationSupported` values are Compatibility Oracle behavior to capture with differential providers for every declared build shape, not values inferred from one-shot or persistent host lifetime. FSharp2 advertises invalidation only when both that compatibility evidence and the live subscription/recheck machinery permit it; otherwise provider-derived reuse is request-scoped unless another complete freshness proof exists. Provider binary and dependency closure, configuration, static arguments, normalized outputs, generated bytes, and invalidation generation are semantic cache inputs. Cross-session reuse requires a separately versioned dependency/freshness contract; otherwise broker restart, invalidation, or unknown provider effects widen invalidation conservatively. Provider diagnostics remain part of family-wide FS Diagnostic Compatibility, and broker startup, probing, queries, normalization, generated output, invalidation, and RPC costs remain separately attributable under the Performance Tripwire. The complete boundary and gate are defined by the [issue #13 research](../research/type-provider-compatibility-boundary.md), applying the cache and evidence principles from the [comparative fast-compiler research](../research/fast-fsharp-compiler-cold-and-incremental.md).
